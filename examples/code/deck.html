Postmortem · price cache

Stale prices lived for eleven minutes

How a two-line invalidation bug hid behind a sixty-second TTL, and what the fix looks like in code.

An illustrative case with invented numbers · Platform team

Open with the symptom, not the code: customers saw yesterday's price for about eleven minutes after every bulk import. The numbers in this deck are made up to tell a realistic story.

The read path

Every price read trusts the cache for sixty seconds

const TTL = 60_000;
const cache = new Map<string, Entry>();

export async function getPrice(sku: string): Promise<number> {
  const hit = cache.get(sku);
  if (hit && hit.expires > Date.now()) return hit.value;

  const value = await db.price(sku);
  cache.set(sku, { value, expires: Date.now() + TTL });
  return value;
}

Step 0: the whole function, it is small. Step 1: the fast path, a fresh entry is returned without asking the database. Step 2: the slow path refills the entry for another sixty seconds. Nothing here can be wrong on its own; the bug is in who else writes prices.

Who writes prices

The bulk import writes to the database and never tells the cache

Two paths touch the price. Shoppers read through the cache. The nightly and ad-hoc bulk import writes straight to Postgres. Click once to see the edge that does not exist: nothing invalidates the entry, so the cache keeps refilling stale values from replicas that lag.

The fix

The fix lives in the writer, not in the reader

export async function importPrices(rows: Row[]) {
  for (const row of rows) {
    await db.upsertPrice(row.sku, row.value);
  }
}

export async function importPrices(rows: Row[]) {
  for (const row of rows) {
    await db.upsertPrice(row.sku, row.value);
    cache.delete(row.sku);
  }
}

export async function importPrices(rows: Row[]) {
  await db.upsertPrices(rows);
  await bus.publish('prices', skus(rows));
}

bus.subscribe('prices', (s) => s.forEach(evict));

The bugThe loop writes and forgets.

The obvious fixDelete the key. It works on one node only.Every other node keeps its stale copy for a minute.

The real fixWrite once, publish once, every node evicts.

Step 0 is the bug: the loop writes and forgets. Step 1: the obvious fix, delete the key. It works on one node only. Step 2: batch the write and publish one event that every node subscribes to. Watch how the function header keeps its place while the loop turns into a batch.

The patch

The patch swaps a loop for one batch and one event

  export async function importPrices(rows: Row[]) {
-   for (const row of rows) {
-     await db.upsertPrice(row.sku, row.value);
-   }
+   await db.upsertPrices(rows);
+   await bus.publish('prices', skus(rows));
  }
+
+ bus.subscribe('prices', (s) => s.forEach(evict));
GoesOne database round trip per row: 10,000 rows, 10,000 trips.
ComesOne batch write, then one event that every node hears.
Closes the loopEach node evicts the SKUs the event names.

Minus is amber, plus is blue, and both carry a sign in the margin, so the slide still reads in greyscale and for colour-blind viewers. Click through: what goes away, what replaces it, and the subscriber that closes the loop. Each callout leaves when the next arrives.

The benchmark · illustrative data

One batch write is thirteen times faster than the loop

  await db.upsertPrice(row.sku, row.value);

const rows = await loadRows(10_000);

Same ten thousand rows, same database. Step 0: the loop, 4,200 ms. Step 1: the batch, 310 ms. The bars grow with the code states because both are driven by the same step numbers. The figures are invented for this example.

The regression test

A test pins it: red before the patch, green after

$ npm test -- price-cache
! FAIL  price-cache.test.ts
! bulk import invalidates cached prices: expected 9, received 7
$ git apply fix-invalidation.patch
$ npm test -- price-cache
PASS  price-cache.test.ts
Tests: 1 passed, 1 total
$ git commit -am "Invalidate cached prices on bulk import"
[main 3f2a9c1] Invalidate cached prices on bulk import

Typing is deterministic: it is driven by the build progress, not by a timer, so a jump or an export shows the same text. Four commands: the test fails on the old code, the patch goes in, the same test passes, the commit.
